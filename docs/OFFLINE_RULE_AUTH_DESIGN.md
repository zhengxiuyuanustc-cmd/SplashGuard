# 离线规则来源验签设计与实现边界（0.1.14候选）

状态：2026-10-27，0.1.14候选已落地来源验签、独立历史账本、本地保存边界及预览确认代码；本地SDK 35未签名构建通过。新增326项检查，合计21个纯Java程序1645项通过。对应源码20227dc的标准debug/未签名release、双lint及纯Java CI均已通过，本地非调试包已签名核对；文件提供者、旋转/进程重建、真实磁盘故障及手机广告仍未验收。公开发行情况另见[验证记录](../TESTING.md)；使用说明见[离线来源验签](OFFLINE_RULE_AUTH.md)。

## 目标与历史缺口

验签只回答“这些原始字节由受信规则发布者签过且未被修改”。签名不能证明规则正确、广告按钮真实、界面未遮挡或广告已关闭。导入仍必须经过现有内置目录和当前有效状态的双重收紧校验；不能新增包名、选择器、脚本、网络地址、动作能力或替用户选择应用。0.1.13暂停的坐标动作也不能由签名文件恢复。

原有`OfflineRuleStore.apply`只在当前包与新包的`id`相同时比较修订号。切换到`local.controls`、撤销或恢复内置后，单靠当前包版本不足以识别曾接收过的旧发布文件。0.1.14以独立`RuleUpdateState`账本弥补这一缺口；普通本地路径仍只作未认证限制。可信更新使用内部`applyAuthenticated`，仅略过当前未认证包的同ID修订比较，保留内置及当前状态的全部收紧校验，避免本地同ID大版本污染可信渠道历史。

## 限定格式与信任根

采用标准JWS Compact的单签名格式，不自创签名算法或把整份载荷塞进JSON字符串。三个部分分别承载受保护头、载荷和签名；验签输入使用原文件的头段、英文句点、载荷段，不能解析后重新序列化再验证。[RFC 7515 §3.1](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1)

以下应用约束已在候选代码中实现：

- 只允许`RS256`，使用`SHA256withRSA`验证；RSA公钥限定2048—4096位、公开指数65537；当前内置信任根为独立3072位公钥。RS256的定义见[RFC 7518 §3.3](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.3)。Android标准`Signature`表列出`SHA256withRSA`自API 1起支持，适合本项目minSdk 26；本地构建已通过，设备验证仍需完成。[Android Signature](https://developer.android.com/reference/java/security/Signature)
- 受保护头恰好包含`alg`、`kid`、`typ`三个不重复字符串字段；值分别为`RS256`、编译内置的可信键编号、`splashguard-rule-limits+jws`。拒绝所有额外字段，包括`jku`、`jwk`、`x5u`、`x5c`、`crit`，拒绝`none`、HMAC及其他算法。
- APK内编译“键编号→公钥、发布者、渠道、允许包ID”的固定映射。文件中的键编号仅用于查询，不能带入公钥、替换信任根或决定网络取钥地址。轮换键必须通过代码审查和App更新，同一发布渠道沿用同一历史账本。
- 规则签名使用独立密钥，未复用APK升级签名密钥。当前可信公钥及范围由`RuleTrust`编译固定，[公开配置](../tools/rule-authority.json)供审查和作者工具比对。作者私钥仅保留于忽略目录中的Windows DPAPI CurrentUser封装，不进入APK或仓库。纯模型检查使用临时测试密钥；独立`RuleTrustTest`另核对内置公开配置和公开示例。

文件仍由本人选择，不增加网络权限，不自动下载、上传或更新。

## 输入及验证边界

总文件上限64 KiB；只接收ASCII的三个非空段，恰好两个分隔句点。拒绝BOM、空白、换行、补位等号、尾随内容、非base64url字符和非规范编码；解码后再编码必须与原段逐字一致。头解码上限256字节，载荷解码上限48000字节，签名字节长度必须等于该内置RSA模数长度。固定上限在分配大缓冲区或执行密码运算前检查。

先严格解码并检查头，再选固定公钥，对原始ASCII头段与载荷段验证。签名有效后，载荷必须通过严格UTF-8和现有`RuleJsonCodec.decodePack`；实际预览/应用还必须通过`RuleUpdateState`和`OfflineRuleStore`校验。保留重复键、未知字段、非整数、重复规则、越界和放宽限制的拒绝行为。签名载荷直接是当前Pack JSON，不做JSON字符串包裹；现有解析器的单字符串长度上限不应因此放宽。

任何失败均不应用文件，不增加账本版本，不保存输入到操作日志。界面使用固定错误分类，避免把原始载荷、URI或异常堆栈展示、导出。只有验签器能构造的不可变`VerifiedPack`类型承载发布者、渠道、原始载荷摘要、原始封装及已解析限制；普通Pack不能自行声明“已认证”。

## 独立历史账本

账本键来自内置映射的`publisher/channel`，不能由文件任意新建。最多16个渠道记录；每项保存已接受的最高修订号、该修订的原始载荷SHA-256及必要的键编号/来源元数据。摘要针对原始UTF-8载荷字节，空白和换行变化也会改变摘要。当前Pack中的修订号作为该渠道的单调发布序号；允许包ID名单防止通过更换`Pack.id`另起历史。

- 新版本低于最高版本：拒绝。
- 相同版本、不同原始载荷摘要：拒绝，即使两份文件都验签成功。
- 相同版本、相同摘要：作为已接收文件提示，不重新应用，不改变当前有效限制或撤销记录；需要恢复时走独立明确的恢复操作。
- 更高版本：只有当前状态的限制校验与持久化均成功后才提高最高值。

暂停某组规则、普通本地限制导入、撤销和恢复内置不得清除或降低账本。恢复内置会明确改变有效规则，但不授权再次接收旧发布文件。普通未签名文件只能按现有“本地未认证限制”路径收紧规则，不能获得发布者标记、推进或替换可信渠道账本。

这只能防止完整本地状态尚在时的历史文件重放，不能保证离线用户已得到最新版本或即时撤销信息。清除App数据、卸载重装、回滚App私有存储或取得高权限后篡改状态均不在本方案保证内；不要宣传绝对防回退。

## 预览、确认和恢复

导入时在副本上完成验签、账本检查及限制模拟，展示发布者/渠道、版本、认证结果和具体限制；此时不保存。保留原始封装仅在受限进程内存中，不把“已解析Pack”当成认证凭据。

本人确认时，对同一份原始封装重新验签，并重新读取当时的有效状态和账本再校验，防止预览后状态变化。候选代码以保留的进程内任务承接旋转；进程重建时若原始封装丢失，清除预览并要求重新选择文件，不恢复认证或自动应用。`Bundle`只存选择器/中断/曾有预览等状态标记，不保存原始封装或已解析Pack。这是代码及纯模型边界，旋转和进程重建的实际UI流程仍待设备验收。

新有效限制、前一步快照、撤销标记、独立账本及来源元数据编码为一个受限JSON快照；`RuleData`在同一`SharedPreferences.Editor`中同步提交快照、认证暂停和隔离标记，同时移除旧规则键。确认前仅在模型副本计算。`RuleStateStorage`对提交返回false或抛错设置本进程故障闩，普通读取和修改停止，不能宣称应用成功。明确恢复时保留后端实际可读、可验证的最高历史，即使失败提交已改变内存，也采用保守处理；损坏记录隔离并暂停签名导入。92项内存后端检查覆盖这些分支，但不等于Android真实磁盘故障、进程中断和重启语义已经实测。Android官方文档说明，`commit()`原子应用本次编辑、同步写入持久存储，并通过返回值报告保存是否成功；这不是本项目已完成真实磁盘故障验收的证据。[SharedPreferences.Editor.commit](https://developer.android.com/reference/android/content/SharedPreferences.Editor#commit())

撤销只恢复有效限制和对应来源说明，账本保持最高值。签名证明的是原始输入载荷，不能把原签名贴到合并后的完整有效快照上并称其“已签名”。快照可以含此前限制和本次部分覆盖，应区分输入来源与合并结果。损坏的账本不可静默清空再导入；恢复内置规则可恢复基本使用，但应保留认证更新暂停状态，等待明确修复路径。
